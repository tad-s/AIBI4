なぜ別構成なのか： 通常RPC get_izakaya_sales は DISTINCT ON (visit_id, item_name, quantity, unit_price) でオーダー粒度を潰すため、「同時注文／連続注文」を分析できない。PoCはこの分析のために order_id・order_seq を保持した専用テーブルを別に作り、原本を保全している。

経路A ｜ 通常ベース分析の構成正規化スター + RPC

原本テーブル群を RPC が結合・重複除去・天気付与し、フラットな明細行を返す。アプリ側が日本語列とカテゴリを付与して集計する。

orders 注文ヘッダ ／ order_items 注文明細 ~282,983行

他に stores（店舗マスタ・緯度経度・location_id）、weather_locations（21地点）、daily_weather（location_id + date が PK）。RPC は天気を LEFT JOIN で自動付与する。カテゴリ列は原本に存在せず、取得後にアプリの分類器が付与する。

経路B ｜ 池袋東口 PoC専用の構成非正規化フラット1枚

原本を1枚に結合・除外適用・分類済みにした専用テーブル。オーダー粒度を保持し、カテゴリは列に保存される。原本は不変。

poc_ikebukuro_items 除外適用済み・order粒度・61,700行（3-5月56,728＋9月4,972）
カラム型説明

receipt_notext伝票番号

索引： idx_poc_visit(visit_id)・idx_poc_order(order_id, order_seq)。RLS： anon / authenticated に SELECT のみ許可（書込は service key 必須）。原本保全： この1枚は原本と独立で、原本（visits / orders / order_items）は一切変更しない。

決定的な違い ｜ オーダー粒度とカテゴリの持ち方

同じ原本から出発しても、2構成は「行が何を1行とするか」と「カテゴリをいつ決めるか」が逆になる。
