# v9 分析経路・カテゴリ分類・除外条件 仕様書

> 作成日: 2026-10-04
> 対象: v9 バックエンド（FastAPI / Railway 本番）
> 目的: 「データ取得」分析と「PoC分析」の**データ源・カテゴリ分類・除外条件**を管理用に明文化する。
> 参照コード: `v9/backend/data_router.py` / `v9/backend/poc/base_table.py` / `v9/backend/poc/classify.py` / `v9/backend/poc/categorize.py`

---

## 0. 全体像（2つの分析経路）

v9 には商品カテゴリを使う分析が **2系統** あり、**データ源もカテゴリの決まり方も別物**。

| | 経路A | 経路B |
|---|---|---|
| UIボタン | **「データ取得」** | **「🍶 テング池袋東口店 PoC分析」**（`poc-btn`） |
| 画面 | 🔬 ベース分析（12項目）タブ | PoCレコメンド分析 |
| 対象店舗 | 全店舗 | 池袋東口店のみ |
| データ源 | 原本テーブル `visits`/`orders`/`order_items`（RPC経由） | PoC専用テーブル `poc_ikebukuro_items` |
| カテゴリの決め方 | 取得のたびに**その場で計算**（ライブ） | テーブルの**保存済み `category` 列を読むだけ**（作り置き） |
| 除外条件 | **かけない**（全店舗・全商品。「除外」判定品も行は残し「その他」化） | **かける**（定食/対象外/コース/宴会等。テーブル作成時に適用済み） |
| コード修正の反映 | 次回「データ取得」から即時（本番は再デプロイ後） | **テーブルを書き換えない限り反映されない** |

```
経路A（データ取得）
  月・店舗を選択 → RPC get_izakaya_sales
    → 原本 visits + orders + order_items を結合して明細取得
    → add_categories() が商品名からカテゴリ列を【その場で】付与   ← classify.py
    → 12項目のベース分析を集計

経路B（PoC分析）
  ボタン押下 → base_table.build()
    → Supabase poc_ikebukuro_items を全件読込（category列は保存済み）
    → PoCレコメンド分析を集計（同時/連続注文など）
```

---

## 1. 経路A ＝「データ取得」ボタン

### 1.1 データ源
- Supabase RPC **`get_izakaya_sales(p_start_date, p_end_date, p_store_ids[])`**（`data_router.py` の `rpc_name`）。
- RPC 内部で原本3テーブル **`visits` / `orders` / `order_items`** を結合。
- 注意: この RPC は `SELECT DISTINCT ON (visit_id, item_name, qty, price)` で**オーダー粒度を潰す**。そのため経路Aでは「同時/連続オーダー」分析はできない（それが経路B＝PoC専用テーブルが必要な理由）。

### 1.2 カテゴリ付与（その場で計算）
- `data_router.py` の取得処理末尾で **`poc.categorize.add_categories(df, "商品名")`** を呼び、`カテゴリ`（11分類）と `フードドリンク`（ドリンク/フード）列を付与。
- 行は**一切落とさない**。分類器が「除外」と判定した商品も、`categorize()` が **`"除外"→"その他"`** に変換して**行は残す**（`categorize.py`）。
- → 経路Aには「除外」という概念がなく、全店舗・全商品が集計対象。

### 1.3 反映タイミング
- カテゴリは取得のたびに再計算されるので、**`classify.py` 等を直せば次の「データ取得」から反映**。
- 本番(Railway)は **再デプロイ後**に反映。

## 2. 経路B ＝「🍶 テング池袋東口店 PoC分析」ボタン

### 2.1 データ源（優先順位つき）
`base_table.build()`（`base_table.py`）が以下の順で読む:

```
① Supabase poc_ikebukuro_items    ← 本命（本番は通常これ）
     ↓ 取得失敗したら
② poc_base.csv.gz（コード同梱バンドル）  ← フォールバック
     ↓ それも無ければ
③ data/池袋東口店/ の生CSV          ← ローカル開発のみ（本番には無い）
```

- `poc_ikebukuro_items` は **池袋東口店のPoC専用物理テーブル**（要件「原本保全のため別テーブル」対応）。原本 `visits`/`orders`/`order_items` は**不変**。
- このテーブルには `category` 列が**既に入っている**（＝作り置き）。

### 2.2 カテゴリの扱い（保存済みを読むだけ）
- `_load_from_supabase()` は `category` 列を**そのまま取得**（`base_table.py`）。実行時に分類計算は**しない**。
- → `classify.py` を直しても、**テーブル/バンドルの `category` 列を作り直さない限りPoCには反映されない**。

### 2.3 母集団フィルタ（テーブル作成時に適用済み）
テーブル/バンドルは、ローカルで生CSVから構築する時（`_build_from_csv`, `base_table.py`）に以下を順に適用済み:

| 順 | 条件 | 実装 |
|---|---|---|
| 1 | `line_type == "M"`（実注文品のみ。S=無料オプション除外） | `df[df["line_type"]=="M"]` |
| 2 | 期間 `2026-03-01 ～ 2026-06-01`（3〜5月） | `PERIOD_START/PERIOD_END` |
| 3 | 時間帯 `14:00〜23:00`（日曜のみ `22:00` まで） | `OPEN_HOUR=14 / CLOSE_DEFAULT=23 / CLOSE_SUNDAY=22` |
| 4 | 定食メニュー・分析対象外メニューを除外 | `_exclusion_names()`（外部ファイル。後述§4） |
| 5 | コース/放題を除外 | `_COURSE_KW=["お好みコース","飲み放題","放題","お好み宴会","宴会コース"]` |
| 6 | 分類器が「除外」判定の品を除外 | `df[df["category"]!="除外"]` |
| 7 | 宴会系（商品名に「宴」）を除外 | `_drop_excluded()` / `_EXCLUDE_ITEM_KW=["宴","ＦＤ"]` |

- **人数 `party_size>=2`・合計数量 `>=15品`** は**テーブル構築時ではなく、各分析側（`analyses.py`）で適用**する母集団条件（分析#1/#4系）。
  - 例: `analyses.py` の `vq[vq>=15]`（来店合計数量15以上）、`party_size>=2`。
- 卓数しきい値: `MIN_TABLES=10`（2品共起）、`MIN3=5`（3連鎖）。

## 3. カテゴリ分類の仕組み（`classify.py`）

商品名 → カテゴリは **2段構え**。判定は上から順:

```
1. 除外リスト完全一致(_EXCLUDE_EXACT) → "除外"
2. マスタ完全一致(_MASTER=外部SQL)    → マスタの値     ←仕組み①
3. ひらがな→カタカナ正規化(_normalize)
4. キーワード含有チェック(ベタ書き)    → 該当カテゴリ    ←仕組み②
     締め→ドリンク→揚げ物→串→海鮮→鍋→サラダ→ヘビー→軽いつまみ の順
5. どれにも当たらない                → "その他"
```

### 仕組み①: マスタ（外部ファイル依存）
- `item_category_master.sql` を読み込んだ「商品名→カテゴリ」完全一致表（**152件**）＋コード内 `POC_OVERRIDES`。
- POS略称（`サイコロステ`→ヘビー、`ナカ`→ドリンク 等）はキーワードで拾えないため、このマスタで分類。
- **探索順（2026-10-04 修正後）**: `v9/backend/poc/item_category_master.sql`（コード同梱）→ `etc/item_category_master.sql`（リポジトリ）。
  - `build_master(None)` でも `POC_OVERRIDES` は効くよう堅牢化済み。

### 仕組み②: キーワード（ソース直書き）
- `classify.py` 内にカテゴリ別キーワード配列をベタ書き（`_DRINK_KW` / `_SHIME_KW` / `_AGEMON_KW` / `_KUSHI_KW` / `_KAISEN_KW` / `_NABE_KW` / `_SALAD_KW` / `_HEAVY_KW` / `_LIGHT_KW`）。
- 商品名に当該文字列が含まれれば該当カテゴリ。

### 11分類 → ベース分析の粗フラグ対応（`analysis_service.py`）
- `_HEAVY_CATS = {揚げ物, 串, ヘビー, 鍋, 締め}`、`_LIGHT_CATS = {サラダ, 軽いつまみ, 海鮮, デザート}`、ドリンク=`ドリンク`。

## 4. 除外条件の全体像（3種類）

「除外」は**用途の違う3つ**が併存する。混同注意。

| # | 種類 | 書いてある場所 | 件数 | 効く経路 |
|---|---|---|---|---|
| ① | 操作ログ・備品の完全一致除外（`_EXCLUDE_EXACT`） | **classify.py にベタ書き** | 9件固定 | 経路B（経路Aでは「その他」化して行は残す） |
| ② | 定食メニュー・分析対象外メニュー | **外部ファイル** `etc/池袋東口店_定食メニュー.txt`（36）＋`etc/分析対象外メニュー.csv`（102） | 138件 | 経路B（テーブル作成時） |
| ③ | コース/放題/宴会・飲み放題 | **classify外・base_table.py にベタ書きキーワード**（`_COURSE_KW` / `_EXCLUDE_ITEM_KW=["宴","ＦＤ"]`） | キーワード数個 | 経路B（テーブル作成時） |

- **経路A（データ取得）はこれらの除外を一切かけない**。①に当たる品も「その他」として集計に残る。
- ②③は**経路Bのテーブル作成時に適用済み**。本番Railwayでは**ファイルを読まず**、適用済みのテーブルを読むだけ（§5参照）。

## 5. ローカル vs クラウド(Railway) の違い【最重要】

### 5.1 Dockerイメージに入るもの / 入らないもの
`Dockerfile.v9` は **`v9/backend/` と `v9/frontend/` だけ**コピー。`.dockerignore` が **`etc/` `data/` `docs/` を除外**。

| パス | Railwayイメージ | 備考 |
|---|---|---|
| `v9/backend/**`（`poc/` 含む） | ✅ 入る | `poc_base.csv.gz`・`item_category_master.sql`(同梱) も含む |
| `v9/frontend/**` | ✅ 入る | |
| `etc/**`（定食txt・対象外csv・マスタSQL原本） | ❌ 入らない | `.dockerignore` で除外 |
| `data/池袋東口店/**`（生CSV） | ❌ 入らない | 機密生データ |

### 5.2 各経路のクラウド挙動

| 経路 | ローカル | クラウド(Railway) |
|---|---|---|
| 経路A カテゴリ | マスタ152件＋キーワード | **再デプロイ後**、同梱マスタ152件＋キーワード（2026-10-04修正で復活） |
| 経路B 除外②③ | 生CSVから適用して構築 | **ファイルは読まない**。適用済みテーブル `poc_ikebukuro_items` を読むだけ（除外は焼き込み済み） |
| 経路B カテゴリ | 同上 | テーブルの保存済み `category` 列をそのまま使用 |

### 5.3 過去にあった落とし穴（2026-10-04 修正済み）
- `item_category_master.sql` が `etc/` のみに存在 → Railwayイメージに入らず、経路Aのマスタが**空**に。
- 結果、クラウドの経路Aで **152件中112件が誤分類**（58件ドリンク→その他、`サイコロステ`→その他 等）。
- 修正: マスタSQLを `v9/backend/poc/` に**同梱**し探索順を「同梱→etc/」に（commit `ce0c615`）。再デプロイで反映。
